# DEEPX DX-M1 AI Accelerator

PCIe NPU (M.2, 25 TOPS) on the Raspberry Pi 5 FFC connector via a carrier
board. Driver, DXRT runtime and demo come from the upstream `meta-deepx-m1`
layer; everything project-specific is a delta in `meta-iot-gateway`.

**Status: development bring-up.** A full-flash dev image is supported. It is
**not** OTA- or production-ready — see [Not production ready](#not-production-ready).

---

## 1. Build

```bash
make dev-deepx
```

Composes `kas/deepx.yml` and enables `IOTGW_ENABLE_DEEPX_DXM1=1` through the
Makefile's `BB_ENV_PASSTHROUGH_ADDITIONS`.

**Do not hand-roll a raw `kas shell` for this.** Passing
`IOTGW_ENABLE_DEEPX_DXM1=1` as a bare environment variable does nothing:
bitbake filters the environment at startup, so a variable survives only if
`BB_ENV_PASSTHROUGH_ADDITIONS` is exported in the same shell. The failure is
silent — the build succeeds with the feature off, the kernel is configured
without the symbol whitelist, and the driver fails later looking like an
unrelated defect.

### Two gates, deliberately separate

| Gate | Mechanism | Effect |
|---|---|---|
| Layer availability | compose `kas/deepx.yml` | `meta-deepx-m1` parses |
| Feature enablement | `IOTGW_ENABLE_DEEPX_DXM1` (default `0`) | kernel whitelist + packages |

Composing the layer must not by itself put a proprietary accelerator driver in
an image. `IOTGW_ENABLE_DEEPX_DXM1=0 make dev-deepx` builds with the layer
present and the feature off.

Enabling the feature **without** the layer halts parsing with a message naming
`make dev-deepx`, rather than a confusing `Nothing PROVIDES dx-rt`.

## 2. What gets installed

`packagegroup-iot-gw-deepx` — modules, runtime, and the project glue:

- `kernel-module-dx-dma`, `kernel-module-dxrt-driver`
- `dx-rt`, `dx-rt-cli` (`dxrtd`, `dxrt-cli`, `run_model`, `dxtop`, `dxbenchmark`)
- `iotgw-deepx-runtime` — service account, device policy, systemd unit

`packagegroup-iot-gw-deepx-demo` adds `dx-rt-examples` and `dx-stream-sample`
(a 77 MB payload: `YoloV5S_PPU.dxnn`, `boat.mp4`, `run.sh`). Split so a future
production profile can take the stack without the demo payload.

## 3. Runtime model

**Module load.** `KERNEL_MODULE_AUTOLOAD` names `dx_dma` only. The vendor ships
`softdep dx_dma pre: dxrt_driver`, so modprobe loads `dxrt_driver` first.
Listing both would be redundant and risk the wrong order.

**Device ownership.** `/dev/dxrt*` is `root:dxrt 0660`. Upstream ships
`MODE="0666"` — world-writable access to a DMA-capable accelerator, which this
distro does not accept. `0660` with a dedicated group is the middle ground:
not world-writable, and not root-only either, so the daemon can run
unprivileged and reach the device through group membership.

**Service.** `dxrtd.service` runs `/usr/bin/dxrtd` as `User=dxrt`, ordered
`After=systemd-modules-load.service`, with `ConditionPathExistsGlob=/dev/dxrt*`
so a board with no card fitted does not crash-loop. Confinement is the usual
set; `PrivateDevices` is deliberately **not** set, as it would hide the device
the daemon exists to drive.

The vendor's SysV script (`dxrt-init`, via `update-rc.d`) is removed: this
distro strips `sysvinit` from `DISTRO_FEATURES`, so it would install and never
run. A dead init script is worse than none — it looks managed when it is not.

## 4. Kernel: symbol whitelist

`CONFIG_TRIM_UNUSED_KSYMS=y` strips exports no in-tree module uses. The driver
needs two of them and fails at modpost without:

```
ERROR: modpost: "get_user_pages_fast" [pci_deepx/dx_dma.ko] undefined!
ERROR: modpost: "sched_set_normal"    [pci_deepx/dx_dma.ko] undefined!
```

Fixed surgically — `CONFIG_UNUSED_KSYMS_WHITELIST` naming exactly those two,
gated on `igw_deepx_dxm1`. Trimming stays at full strength on every other
image. Add a symbol only when modpost names it, and record the log line that
did: `meta-iot-gateway/recipes-kernel/linux/files/deepx-dxm1-ksyms.txt`.

**Kbuild silently ignores a whitelist path that does not exist** — it is not an
error. The kernel bbappend therefore `bbfatal`s if the file fails to reach the
srctree.

## 5. Module signing

Modules are signed by **Kbuild**, via `CONFIG_MODULE_SIG_ALL=y` during
`modules_install` (the driver's `install` target routes through it). Kbuild is
the single signing authority; `iotgw-kernel-module-signing.bbclass` only
*verifies*, failing the build if any `.ko` lacks the exact 28-byte signature
trailer.

Do not add a second signer. If a recipe installs `.ko` files without going
through `modules_install`, the verification fails — correctly — and the fix is
to route it through `modules_install`.

## 6. Not production ready

The kernel's module-signing key is **autogenerated per kernel build**, so a
module only loads on the kernel built alongside it. A full-flash dev image is
fine because it carries a matched pair. These block anything beyond that:

- **Persistent signing key** via `CONFIG_MODULE_SIG_KEY`, shaped like the FIT
  key in `kas/local.yml` ([FIT_BOOT_SIGNING.md](FIT_BOOT_SIGNING.md)).
- **Fail-closed kernel/module pairing.** `bundle-hooks-fit.sh`'s guard reads
  `expected_release` from the bootfiles archive, and `IOTGW_RAUC_UPDATE_BOOTFILES`
  defaults to `0` — so a rootfs-only bundle has no archive and the mismatch
  check silently passes. A rootfs-only OTA could deliver a module the running
  kernel refuses, giving a dead accelerator with no RAUC failure and nothing in
  the update log.
- **sstate and retired keys.** The signature is produced inside `do_install`,
  so its sstate object is only as trustworthy as the key that made it.
- **Signed model delivery / model-OTA** — deferred to the same milestone.

## 7. Licensing

Every DEEPX package is `LICENSE = "Proprietary"` under a customer-only licence:
the software is supplied to customers with a DEEPX NPU, and sharing is
prohibited. `MODULE_LICENSE("GPL")` in the driver source governs only kernel
symbol eligibility — it is **not** the recipe's legal licence, and is not a
reason to change `LICENSE`.

Nothing proprietary is committed to this repository: the SDK, model and video
live in the pinned upstream layer under `.kas/` (gitignored).

> **An image built with this feature must not be redistributed.**

A reusable acceptance gate for proprietary accelerator packages is outstanding
and should land before `dx-stream` or further demo packages are wired in.

## 8. Hardware notes

- The Pi 5's external PCIe is a **single-lane FFC connector**, so the link
  trains at x1 against the card's x4 capability. This is the board, not the
  SoC: BCM2712 has a 4-lane controller, already used by the RP1 south bridge
  (`pcie@1000120000`, `num-lanes=4`). Not worth chasing.
- The link trains at Gen2 (5GT/s) by default. `dtparam=pciex1_gen=3` is a
  **no-op on this DTB** — `__overrides__` exports only `name`, `rtc` and
  `rtc_bbat_vchg`, so the parameter is silently ignored. Raising the speed
  needs a DTS change (`max-link-speed`) or a shipped `.dtbo`; note that
  `/boot/overlays` is not populated at all
  (`RPI_KERNEL_DEVICETREE_OVERLAYS = ""`), so `dtoverlay=` lines in
  `config.txt` currently do nothing either.
- A TPM on the GPIO header may physically conflict with an accelerator carrier.
